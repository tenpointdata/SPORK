# Stylometry and perceptual image hashes: more identity signal, indexes and clustering

Status: design note, slice 1 implemented, 2026-11-02. Feeds slice 3 ("soft evidence") of
`04-identity-resolution-design.md` and the calibration pipeline of `05-identity-model-mlops.md`.
Goals served: **I** (identity layer), **S** (set-oriented: cluster a selection), **R** (index-backed near-duplicate lookup).

## 1. Problem

Identity resolution today scores identifiers that match exactly: a phone, an email, a handle, an upstream image hash.
Two kinds of evidence escape it:

- **The same photo, re-encoded.** A re-posted photo is resized, recompressed, cropped or mirrored by the aggregator or the
  poster, so its upstream hash and its content SHA differ. A perceptual hash stays within a few bits.
- **The same writer.** Ads with no identifier in common are often written by one hand: the same emoji, the same
  misspellings, the same "txt me ONLY". Recon already uses a 24-d style vector for this (`analysis/style.ts`, cosine 0.95).

Both are also wanted outside identity resolution: as indexes (find every re-post of this photo), as clustering (group
a selection by photo or by author), and as features for the model.

## 2. What is built (slice 1)

No new dependency: image decoding is the JDK's ImageIO (JPEG, PNG, GIF, BMP). WebP and HEIC need a decoder plugin, an
open question (7).

### 2.1 Style: two vectors, two jobs

- **`style.vector` / `reconStyleVector` (`style24@v1`).** Kept bit-exact because Recon thresholds it at 0.95 and
  `01-architecture.md` stores it as `Record.styleVec`. It is coarse: 20 function-word rates and 4 punctuation rates,
  so two ads that use none of the function words collapse onto the punctuation axes, and short ads are noisy. Use it for
  parity, not as the main authorship signal.
- **`style.profile` (`styleNgram@v1`).** Character n-grams are the strongest classical feature for short-text
  authorship: they catch spelling, emoji habits, spacing, capitalization and punctuation at once. Before hashing,
  **URLs, emails and digits are masked** (digits become `0`, so "555-1234" vs "(555) 1234" stays a habit while the
  number goes): a phone is identity evidence of its own, and letting it into the style would count a shared phone
  twice. 256 dimensions by default (1 KB as float32), stored in an `LSM_VECTOR` cosine index for corpus-wide "same
  author" kNN, exactly like the existing style index.

Thresholds for the profile are **not calibrated yet** (7). On the test fixture's two invented authors the profile scores
same-author pairs 0.71 to 0.90 and cross-author pairs 0.05 to 0.10, while Recon's 24-d vector scores author A's pairs
0.98 but author B's only 0.85, under its 0.95 cut: an illustration of the coarseness above, not a measurement.

### 2.2 Images: which hash for what

| Method | Bits | Robust to | Use |
|---|---|---|---|
| aHash | 64 | resize, recompression | cheapest; many false positives on simple images |
| dHash | 64 | resize, brightness | good cheap default for exact-ish re-posts |
| pHash | 64 | resize, recompression, mild edits | the 64-bit default (`image.perceptualHash(img)`) |
| PDQ | 256 | as pHash, plus better separation; dihedral variants cheap | the corpus default where 256 bits fit (S-PDQ in `01-architecture.md` 4c) |

Distances: about 12% of the bits is the usual near-duplicate cut (8 of 64 for pHash, 31 of 256 for PDQ), and the
procedures default to it. Mirrored re-posts are caught by probing with the 8 dihedral hashes
(`image.perceptualHash(img, 'pdq', true)`).

**Quality gate.** A featureless image (blank, solid, a logo on a flat background) hashes to noise around a flat signal
and collides with every other featureless image. `image.quality` is PDQ's gradient score; store it next to the hash and
pass `qualityProperty` to the procedures, which then ignore hashes scoring below `minQuality` (50, PDQ's guidance). The
tests show two grey squares clustering without the gate and not with it.

**Parity.** pHash here follows the published algorithm but resamples with an area average, not Pillow's Lanczos, so
its bits differ from Python `imagehash`: store the method with the hash. PDQ is bit-identical to Meta's Java reference
since WS12 (`PdqHasher`, golden-tested on the reference's own regression images, `workstreams/ws12-pdq.md`), so PDQ
hashes compare with hash lists made elsewhere (NCMEC, ThreatExchange). `image.pdq(img)` returns the hash and quality in
one call. PDQ hashes computed before WS12 (subsampled decode, area resampling) are a few bits off and should be
recomputed; none were stored.

## 3. Indexes

### 3.1 Near-duplicate lookup on an ordinary LSM index (multi-index hashing)

Cut a b-bit hash into `bands` chunks of at most 32 bits and store one LONG key per chunk (tagged with its band). Any
hash within distance r of a query differs in at most floor(r / bands) bits in at least one band (pigeonhole), so looking
up every chunk value within that radius of the query's chunks misses nothing; candidates are verified with the full
distance.

```sql
CREATE PROPERTY Image.pdq STRING;
CREATE PROPERTY Image.pdqQuality INTEGER;
CREATE PROPERTY Image.pdqBands LIST OF LONG;
CREATE INDEX ON Image (pdqBands BY ITEM) NOTUNIQUE;
UPDATE Image SET pdq = image.perceptualHash(bytes, 'pdq'), pdqQuality = image.quality(bytes);
UPDATE Image SET pdqBands = hamming.bandKeys(pdq, 8);
```

```cypher
CALL similarity.hash.neighbors($pdq, {type: 'Image', property: 'pdq', bandsProperty: 'pdqBands', bands: 8,
                                      maxDistance: 15, qualityProperty: 'pdqQuality'})
YIELD node, distance, similarity
```

or in SQL: `SELECT FROM Image WHERE pdqBands CONTAINSANY hamming.probeKeys(:q, 8, 15) AND hamming.distance(pdq, :q) <= 15`.
`hamming.bandKeys` of a list of hashes is the union of their keys, so one property indexes every image of a record.

**Choosing bands.** Chunks of about log2(N) bits make each key match about one stored hash (`HammingBands.suggestBands`).
The probe count is bands x the size of a Hamming ball of radius floor(r / bands), so the radius sets the cost:

| Hash | N per period | bands | maxDistance | probe keys | random candidates to verify (probes x N / 2^chunk) | index entries per image |
|---|---|---|---|---|---|---|
| PDQ 256 | 75M | 8 (32-bit) | 15 | 264 | about 5 | 8 |
| PDQ 256 | 75M | 8 | 23 | 4,232 | about 75 | 8 |
| PDQ 256 | 75M | 8 | 31 | 43,912 | about 770 | 8 |
| PDQ 256 | 75M | 16 (16-bit) | 31 | 272 | about 311,000 | 16 |
| pHash 64 | 75M | 2 (32-bit) | 5 | 1,058 | about 18 | 2 |
| pHash 64 | 75M | 2 | 7 | 10,978 | about 190 | 2 |
| pHash 64 | 75M | 4 (16-bit) | 7 | 68 | about 78,000 | 4 |

Real hashes cluster, so these are lower bounds. So: **index lookups for re-encodes and resizes (PDQ within 15), not for
the full 31-bit PDQ radius**.
The wide radius belongs to set-scoped work (3.2) and to the S-PDQ `LSM_IVF_VECTOR` index of `01-architecture.md` 4c.
An index point lookup is a few microseconds warm, so 264 probes cost about 1 ms and 43,912 about 0.1 to 0.4 s.

**Storage.** An LSM entry is about 18 B (8 B key, compressed RID, overhead), so 8 bands cost about 150 B per distinct
image: 200 GB at 1.35B images (3x), against S-PDQ's 54 GB. That does not fit beside the architecture budget corpus-wide.
A pHash variant with 2 bands would be about 36 B per image (49 GB at 3x, radius 5).

**Decision (architecture session, 2026-11-02): no corpus-wide Hamming band index.** PDQ band indexes (8 bands) go only
on the hot-tier media databases and on case databases, which also covers ingest-time dedup against the hot window.
Corpus-wide, wide-radius near-duplicate search is the S-PDQ IVF space (`01-architecture.md` 4c.1), and pHash is not
stored corpus-wide, since PDQ supersedes it. The hot-tier band bytes are carried in `model/budget.py`. pHash and the other
64-bit methods stay available as functions, for set-scoped work and for analysts' own types.

### 3.2 Set-scoped radius search

`HammingIndex` holds the hashes of a selection in memory: pairwise below 2,048 hashes, multi-index hashing above, sorted
`long[]` band tables, no per-candidate allocation. It is what `similarity.cluster` and `similarity.compare` use, at any
radius, since the cost is bounded by the selection, not the corpus.

### 3.3 Style

Writing style needs no new index: the profile is a dense vector for `LSM_VECTOR` (cosine), and Recon's fingerprint is
a string for an ordinary index (equality groups, as Recon's `authorship` detector does).

## 4. Clustering

```cypher
// near-duplicate photos in a selection, re-posts of re-posts chained together
CALL similarity.cluster($records, {property: 'imagePhashes', metric: 'hamming', qualityProperty: 'imageQuality'})
YIELD clusterId, key, size, members, links, cohesion

// authors in a selection, Recon's greedy rule (no chaining)
CALL similarity.cluster($records, {property: 'text', metric: 'cosine', threshold: 0.95, styleMethod: 'recon'})
YIELD key, members
```

| Option | Meaning | Default |
|---|---|---|
| `property` | Hash(es) for hamming; a vector or a text (styled on the fly) for cosine | required |
| `metric` | `hamming` or `cosine` | required |
| `threshold` | Max distance (hamming) or min cosine | 8 / 31 bits by width; 0.95 |
| `linkage` | `single` (connected components) or `leader` (Recon's greedy `authorshipClusters`) | single for hamming, leader for cosine |
| `styleMethod` | For text: `profile` or `recon` | profile |
| `qualityProperty`, `minQuality` | Ignore hashes of images scoring below | none, 50 |
| `minSize`, `limit`, `memberLimit` | Rows kept and members listed | 2, all, 1000 |
| `maxRecords` | Refuse bigger inputs | 1,000,000 hamming; 10,000 cosine (it compares every pair) |

`records` (and either cluster of `similarity.compare`) may also be the name of a saved selection (`selection.save`,
`03-f1-selections-design.md`), read in RID order. `key` is stable across calls and input orders (the smallest hash of the group for hamming, the smallest RID for
cosine), so a group can be written once and merged into on the next run. Recon's extra rule (an author cluster must
span at least 2 phones) stays in Recon.

## 5. Identity resolution: two routes

### 5.1 Now: clusters as identifiers (no model change)

`identity.compare`, `cohesion` and `candidates` score any node reached over `via` as an identifier whose kind is its
type. So a group from `similarity.cluster` written as a node is immediately a new kind of evidence, with term-frequency
adjustment from its size and the usual time hazard:

```
(:Record)-[:HAS_IMAGE_CLUSTER]->(:ImageCluster {key, recordCount})
(:Record)-[:HAS_STYLE_CLUSTER]->(:StyleCluster {key, recordCount})
```

`SimilarityProceduresTest.imageClustersBecomeIdentityEvidence` does exactly this and gets a SHARED `ImageCluster` term
from `identity.compare`. Starting kind settings, to be calibrated (`05-identity-model-mlops.md`):

```
ImageCluster: {m: 0.4, concurrent: 0.002, handoff: 0.05, halfLifeDays: 0}
StyleCluster: {m: 0.3, concurrent: 0.05,  handoff: 0.10, halfLifeDays: 365}
```

**The two signals answer different questions, and that matters more here than anywhere else.** A shared photo
usually means the same person, except stock and stolen photos, which the frequency term discounts once they are reused
widely. A shared writing style more often means the same **writer**, and in trafficking the writer is frequently the
operator posting for several people. So `StyleCluster` gets a low m and a high `concurrent` hazard for "same
individual", and is a strong signal for the operator network view (the link-analysis layer), not a merge signal.

### 5.2 Next: soft terms in the model (slice 3, identity session)

`similarity.compare(clusterA, clusterB, options)` returns the raw features (style pairs above threshold, max, mean best
match, centroid cosine; near and exact image pairs, minimum distance), built on `ClusterSimilarity`. Inside the model
the identity session uses `SoftSimilarity` (agreed API, 2026-11-02): per-member style vectors and image hashes carried in
the cluster profile as primitive arrays, and pair statistics with skip indexes so cohesion's leave-one-out views need no
copy. Slice 3 turns them into SOFT likelihood-ratio terms from calibrated tables (never the raw
cosine), and `identity.features` exports them for training. The two routes coexist: 5.1 makes the evidence usable today
and gives blocking (`identity.candidates`) something to block on; 5.2 replaces the hard group boundary with a graded
score.

**Status (2026-11-03): wired by the identity session** (`04-identity-resolution-design.md` 2.9). `identity.compare`,
`cohesion` and `candidates` take `styleProperty`, `styleRecon` and `imageHashProperty`, plus
`soft.{style, image}.{threshold or maxDistance, m, falseMatchRate, concurrent}`. Each signal is one SOFT term with
P(agree | same) = m and P(agree | different) = c + (1 - c)(1 - (1 - falseMatchRate)^pairs). With the defaults, style
stays weak (about 2 bits at most) and one near-duplicate image is worth about 7.6 bits. `identity.features` exports the
raw `SoftSimilarity` statistics under `soft.style` and `soft.image`. Unless `soft.image.maxDistance` is set, the image cut
follows the hash width, as in the `similarity.*` procedures: 8 bits for 64-bit hashes, 31 for PDQ, about 12% of the bits
otherwise; `identity.features` reports the cut it used.

## 6. Cost

- `style.vector`: one pass over the text. `style.profile`: three passes of n-grams, one `float[dims]`, no per-n-gram
  allocation; about 50 us per 90-character ad on the same loaded machine.
- `image.perceptualHash`: dominated by decoding: PDQ measured 7 ms for a 320x240 JPEG and 64 ms for a 3000x2000 JPEG on
  a heavily loaded laptop (load average above 50), so ingest-time hashing belongs in the enrichment pipeline, not on the
  read path. Large images are subsampled while decoding (short side at least 512),
  then one area resize; the PDQ box filter is two running-sum passes per axis. Declared sizes above 64M pixels and
  arguments above 32 MB are refused before decoding (decompression bombs); decoding is in memory only (no ImageIO cache
  file).
- `similarity.cluster` (hamming): O(hashes) to build the tables plus the probes; (cosine): every pair, which is why it
  caps at 10,000 records. Loops run under the command's `WorkGuard`.

## 7. Open questions

1. **Calibration.** Profile thresholds, Hamming cuts per method and the kind settings in 5.1 need labelled Recon pairs
   (`05-identity-model-mlops.md`). Until then use them as rankings.
2. **PDQ reference parity.** Done (WS12): bit-identical to the Java reference on its regression images.
3. **WebP and HEIC.** Not decodable by the JDK; a TwelveMonkeys ImageIO plugin (BSD-3) would add them, a new dependency to
   approve.
4. **Budget.** Decided: no corpus-wide band index; PDQ bands on hot-tier media and case databases only (3.1).
5. **Learned authorship.** `01-architecture.md` lists LUAR (Apache-2.0) as an optional S-STYLE leg; the n-gram profile is
   the model-free baseline it has to beat on labelled operator clusters.
6. **Agency templates.** Ads written from one template by an agency will cluster by style across many people; the
   identity model's `concurrent` hazard and cohesion (G2) should catch them, to be measured.
